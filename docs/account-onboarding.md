## Поведение

После успешного `POST /api/v1/auth/register` новый соискатель или работодатель
попадает на `/onboarding`. Роль выбирается при регистрации и не меняется от
ответа «Школьник», «Студент» или «Другое». Старые аккаунты не включаются в опрос;
администратор, созданный командой сервера, также не включается.

1. Кто вы: школьник, студент университета, выпускник, сейчас не работаете или другое.
2. Что важнее: новая работа, стажировка или просмотр возможностей.
3. Город из общего справочника городов Казахстана.
4. Профессия или интересующая сфера.
5. Источник знакомства с JobHub: Telegram, Instagram, Google, друг, университет,
   другое или пропуск.

Первые четыре ответа обязательны. Для «Другое» требуется свой текст, но неполный
текст можно сохранить как черновик. Пятый вопрос необязателен; «Пропустить»
очищает его пользовательский текст и сохраняет `referral=skip`. Интерфейс
доступен на `kk` и `ru`; значения в API не зависят от языка.

## Сохранение и навигация

- Изменения автоматически сохраняются через 350 мс после последнего ввода;
  текстовые поля также сохраняются при потере фокуса.
- «Назад», «Продолжить» и «Сохранить и выйти» ждут ответа сервера. При ошибке
  переход не выполняется, введённый текст остаётся на экране.
- При закрытии вкладки с ещё не сохранённым ответом браузер может показать
  предупреждение. Надёжнее дождаться «Сохранено» или выбрать «Сохранить и выйти».
  Мгновенное принудительное закрытие браузера до ответа сервера не гарантирует
  сохранение последнего ввода.
- После повторного входа, в том числе с другого устройства, загружаются ответы
  и последний сохранённый шаг. `OnboardingGate` возвращает незавершённый аккаунт
  к опросу при переходе на другие страницы.
- После завершения `completed_at` сохраняется в БД. Последующие входы и прямой
  переход на `/onboarding` не открывают опрос заново.
- После завершения используется безопасный `returnTo`, иначе `/profile`,
  `/employer` или `/admin` в зависимости от роли. Внешние URL и возврат в цикл
  `/login`, `/register`, `/onboarding` не допускаются.

Ответы хранятся отдельно от `candidate_profiles`; они пока не изменяют резюме,
профиль или алгоритм рекомендаций автоматически.

## API

Все пути ниже имеют префикс `/api/v1`. В ответах регистрации, входа и `/auth/me`
добавлено поле `onboarding_required`.

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `GET /auth/onboarding` | Активная сессия | Собственные ответы, шаг, версия и состояние завершения |
| `PUT /auth/onboarding` | Активная сессия, trusted origin, `X-CSRF-Token` | Сохранённый черновик или завершённый опрос |

Пример тела сохранения черновика, без реальных данных пользователей:

```json
{
  "persona": "university_student",
  "persona_other": "",
  "goal": "internship",
  "city_id": "almaty",
  "profession": "Разработка",
  "referral": "",
  "referral_other": "",
  "step": 5,
  "version": 3,
  "complete": false
}
```

Для завершения передайте `complete=true` и `step=5`. Пропущенный источник
нормализуется в `skip`. Сервер проверяет enum, город, обязательные ответы и длину
текста (не более 200 символов). Ответ содержит те же поля ответов плюс `required`,
`version` и `completed_at`; поле `complete` в ответ не входит.

Коды ошибок: `400` — некорректный JSON/поля/ответы; `401` — нет активной сессии;
`403` — origin или CSRF; `409` — устаревшая версия либо уже завершённый опрос;
`500` — ошибка хранения. `user_id` не принимается от клиента: используется
только ID текущей сессии.

## База и выпуск

Миграция `000015_create_account_onboarding` создаёт `jobhub.account_onboarding`.
Одна строка на пользователя (`user_id` — PK/FK, каскадное удаление). Поля:
ответы, `step` (1–5), `version`, `completed_at`, `created_at`, `updated_at`.
Включён RLS без публичных политик, как для остальных приватных таблиц JobHub.
Доступ выполняется доверенным серверным подключением Go API, не Supabase SDK
в браузере.

Строка создаётся в одной транзакции с регистрацией. Сохранение использует
условие `WHERE user_id=$1 AND version=$10 AND completed_at IS NULL` и увеличивает
версию. Поэтому старая вкладка не перезапишет новые ответы или завершение.
При `409` нужно загрузить актуальные ответы. Завершённая строка не обновляется.

Перед выпуском **необходимо применить миграцию 000015 к целевой базе перед
переключением API**. Новый код авторизации читает эту таблицу; без неё вход и
регистрация не готовы к работе. Не запускайте удалённую миграцию автоматически
и не подставляйте production `DATABASE_URL` в интеграционные тесты. Используйте
существующий [runbook миграций](/docs/migration-runbook) после проверки окружения.
Откат `down` удалит ответы и должен рассматриваться как потеря данных.

## Код и проверки

- `frontend/src/pages/OnboardingPage.tsx`: форма, очередь сохранений, обработка ошибок.
- `frontend/src/app/OnboardingGate.tsx`: восстановление незавершённого опроса.
- `frontend/src/api/http/HttpAuthRepository.ts`: типизированные GET/PUT.
- `frontend/src/lib/onboarding.ts`: безопасные маршруты возврата.
- `backend/internal/auth/onboarding.go`: проверка и хранение ответов.
- `backend/internal/handlers/onboarding.go`: сессия, origin и CSRF.
- `backend/internal/auth/onboarding_test.go`: варианты, обязательность, лимиты.
- `backend/internal/auth/onboarding_integration_test.go`: регистрация, черновик,
  разные сессии, завершение, конфликт версий и старый аккаунт. Запускается только
  при явном `TEST_DATABASE_URL` на изолированную локальную базу.
- `backend/internal/handlers/onboarding_test.go`: защита доступа и HTTP-ошибки.

```sh
cd frontend
npm run typecheck
npm run lint
npm run build
```

```sh
cd backend
go test ./internal/auth ./internal/handlers
go test ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Для ручной проверки
используйте новый тестовый аккаунт в изолированной локальной базе: пройти часть
опроса, выйти, войти на другом устройстве, завершить, снова войти. Проверьте оба
языка, «Другое», пропуск источника, отказ сети и конфликт двух вкладок.
