# Архитектура поставки вакансий

**Исторический архитектурный обзор от 24 сентября 2026 года.** Документ
сам по себе не разрешает миграции, изменение API, провайдеров или Production.

## Исходный путь импорта

```text
Поиск Jooble REST -> клиент и DTO Jooble -> нормализация
  -> устранение повторов по внешнему ID в запуске
  -> атомарный upsert PostgreSQL
  -> общая проверка публичной видимости
  -> GET /api/v1/jobs и GET /api/v1/jobs/:id
```

| Область | Найденное поведение на момент обзора | Оценка |
| --- | --- | --- |
| Реестр | `jobhub.job_sources`: источник, провайдер, рынок, имя, включение, разрешение Production, атрибуция | Хорошая основа |
| Происхождение | У вакансии есть source, external ID, URL, издатель агрегатора, исходная компания и времена провайдера | Достаточно для новых источников |
| Идентичность | `UNIQUE(source, external_id)` отделяет собственные и внешние записи | Сохранить |
| Компания | Необязательная `company_sources` без вымышленного работодателя и объединения по имени | Правильно; Jooble не даёт стабильный employer ID |
| Отклик | У `source=jobhub` — внутренняя заявка; у импорта — внешний URL | Разделение сохраняется |
| Нормализация | Jooble передаёт ID, ссылку, источник, исходные компанию/место/зарплату и сниппет | Неизвестное остаётся неизвестным |
| Устранение повторов | Map по внешнему ID внутри одного запуска | Достаточно для одного источника |
| Сохранение | `ON CONFLICT (source, external_id)` сохраняет UUID и `first_seen_at`; защита от старого наблюдения | Идемпотентно |
| Атомарность | Advisory lock источника, записи и счётчики в одной транзакции | Ошибка откатывает свежесть |
| Ошибка провайдера | Неудачный запрос фиксируется до сохранения вакансий | Не создаёт ложной актуальности |
| Метрики запуска | Статус, поиски, запросы, получено/нормализовано/вставлено/обновлено/пропущено, безопасные ошибки | POC-аудит |
| Актуальность | Успех обновляет first/last seen, sync и `fresh_until` | Политика пока в коде сервиса |
| Видимость | `job_is_public` разделяет жизненные циклы; Production требует разрешение источника | Сильная защита |
| API | Список, счётчик и детали используют одинаковые правила и внешний CTA | Последовательно |
| Ключ Jooble | Только backend, лимит запросов, без ключа в URL лога | Сохранить |

Схема уже содержит nullable поля времени внешнего создания, публикации,
обновления, истечения и архивации. Адаптер заполняет только явно полученные
значения. Отдельная колонка под каждого провайдера не нужна.

## Пробелы перед вторым провайдером

1. Интерфейс сервиса привязан к Jooble (`JoobleSearcher`, `RunJooble`).
2. Политика свежести передаётся сервису, а не описана в реестре источника.
3. Нет сверки отсутствующих вакансий полного снимка. Для ранжированного
   поиска Jooble это правильно, но полному feed понадобится отдельный этап.
4. Поля жизненного цикла внешних вакансий есть, но Jooble даёт только
   `updated`; статус остаётся `unknown` до истечения свежести.
5. Запуск хранит грубые счётчики, но не безопасную область поиска,
   cursor/page, полноту, watermark и число некорректных записей.
6. Нет диагностики повторов между провайдерами.
7. Метаданные прав минимальны: нужны разрешённые поля, версия условий,
   дата согласования, атрибуция и срок удаления. Сначала это может быть
   конфигурация/документация; миграция должна опираться на реальные данные.
8. Логи и строки запусков есть, сводки по источнику пока нет.

Эти пробелы не требуют переписывать работающий Jooble POC немедленно.

## Универсальная модель провайдера

Адаптер отвечает за транспорт и особенности источника; оркестратор — за
лимиты и атомарное сохранение:

```text
Fetch(scope, cursor, budget) -> страница провайдера и расход запросов
  -> Normalize -> ImportedJob и причины пропуска
  -> проверка ID, URL, содержимого и разрешений
  -> устранение повторов по (source, external_id)
  -> атомарный upsert и, если допустимо, сверка полного снимка
  -> политика актуальности/жизненного цикла источника
  -> общая публичная видимость -> API вакансий
```

Будущий интерфейс может объявлять стабильный `Source()`, возможности,
ограниченный `Fetch`, нормализацию с причинами ошибок, тип выдачи
(частичная/полная/event), watermark и документированные события закрытия.
Каноническая модель остаётся независимой от провайдера: без колонок
`jooble_*`, `enbek_*`, `hh_*`. Сырые диагностические payload допускаются
только по договору и с ограниченным сроком хранения вне публичной таблицы.

Перед сохранением у каждой импортированной вакансии должны быть
зарегистрированный включённый источник, непустые внешний ID и название,
безопасный публичный HTTPS URL без credentials, внешний способ отклика,
время наблюдения и честный признак `snippet`/`full`. Нельзя выдумывать
зарплату, дату публикации, компанию или статус. Технически корректная
вакансия неподтверждённого источника всё равно скрыта в Production.

## Актуальность и жизненный цикл

Собственные вакансии сохраняют отдельные публикацию, срок, модерацию,
владение и состояние компании. Политика импорта их не закрывает.

| Параметр политики источника | Зачем нужен |
| --- | --- |
| Интервал обновления | Обнаружение задержки scheduler/провайдера |
| Максимальный возраст показа | Скрытие при отсутствии сигналов закрытия |
| Полнота выдачи | Значение отсутствия вакансии в ответе |
| Поля закрытия/удаления | Немедленная реакция на событие источника |
| Порог отсутствия | Один или несколько полных успешных снимков до действия |
| Действие при удалении | Скрытие, tombstone или очистка по договору |
| Атрибуция и допустимые поля | Контроль публичного ответа |
| Production-разрешение | Финальный фильтр видимости |

Порядок применения сигналов:

1. Документированные `removed`, `archived`, `expired`, `closed` скрывают
   запись сразу с соответствующим статусом и временем.
2. Срок провайдера скрывает вакансию при наступлении, если позднее обновление
   явно не продлило его.
3. Отсутствие в **полном успешном снимке** имеет значение только согласно
   утверждённой политике конкретного источника.
4. Отсутствие в ранжированном поиске, ограниченных страницах, фильтре или
   неудачном запуске никогда не доказывает закрытие.
5. Без сигналов закрытия используется срок `fresh_until` по политике
   источника: после него запись устарела, но не объявлена закрытой провайдером.

Иллюстрации, зависящие от согласования: Jooble POC — частичный поиск без
сверки исчезнувших; Enbek — только после доказанного полного активного
снимка; доска ATS работодателя — полный разрешённый снимок с коротким
окном подтверждения или вторым успехом перед скрытием отсутствующей записи.
Неудачный запуск не меняет времена и статусы вакансий; частичный успешный
обновляет только возвращённые записи.

## Поиск возможных повторов между источниками

`UNIQUE(source, external_id)` остаётся единственным автоматическим
объединением идентичности. Нельзя сливать компании/вакансии или удалять
предполагаемые повторы только по названию.

Будущая диагностика формирует пары кандидатов с оценкой, причинами, временем
и статусом проверки. Сигналы: одинаковый канонический URL работодателя,
подтверждённая связь компании с источником, название и место, близкие даты,
совместимые валюта/период/сумма, сходство описаний и номер requisition.

- Очень высокая уверенность: одинаковый URL вакансии работодателя либо
  явное сопоставление ID от провайдера.
- Высокая: подтверждённая компания, сильное совпадение названия/места/
  описания и совместимые даты.
- Средняя: сырое имя компании, название, место и дополнительные признаки;
  только диагностика.
- Низкая: только название и город; влияет лишь на метрики.

Возможная политика показа позже предпочитает собственную разрешённую
вакансию, затем прямой feed работодателя, затем агрегатор, сохраняя
происхождение и обязанность удаления каждой записи. Основание — измеренные
повторы в Казахстане, не синтетические примеры.

## Наблюдаемость источников

Нужна внутренняя серверная сводка, сначала допустима в SQL/логах:
активные вакансии, получено/нормализовано, вставлено/обновлено/пропущено,
устаревшие/скрытые, ошибки, последний успех, расход запросов, кандидаты
в дубликаты, причины некорректных записей, доля пропущенной зарплаты/
компании, распределение возраста. Сигналы тревоги: повторные сбои,
задержка, резкий спад/рост, исчерпание квоты, ошибки данных, устаревание,
истечение прав и очередь удаления. Секреты и сырые приватные payload в
логах запрещены.

## Масштабирование

- **100 вакансий:** Jooble остаётся ограниченным POC; проверяйте свежесть и
  повторы на небольшой выборке, подключайте разрешённые ATS, ведите контакты
  и письменные разрешения.
- **500–1000:** Enbek только после критериев стратегии; полный снимок с
  политикой источника, внутренний health и контроль квоты до ускорения.
- **10 000:** устойчивые квоты и SLA, инкрементальная/разделённая
  синхронизация, отдельное расписание с jitter/backoff и блокировкой по
  источнику, краткоживущие артефакты, безопасный replay, индексы по
  измеренным планам и аудит удаления.

При любом масштабе Production-показ зависит от разрешения, актуальности,
происхождения и внешнего способа отклика.

## Контрольный список для нового провайдера

- Бюджет запросов ограничен кодом и записан в запуск.
- Ключи только на сервере; секреты и URL с ключом не попадают в логи.
- У нового источника Production-разрешение по умолчанию выключено.
- Перед записью выполняются нормализация и проверка.
- Повторы внутри источника и атомарный upsert обработаны.
- Неудачный/частичный запуск не освежает отсутствующие записи.
- Атрибуция и разрешённые поля следуют письменному договору.
- Отклик внешний; нет вымышленных работодателей и внутренних откликов.
- Сверка исчезновения включается только для документированного полного feed.
- Источник можно сразу выключить; правила удаления проверены до Production.
